# 数据校验规则契约（前后端同步维护机制）

> 本文档是前后端校验规则的**同步维护契约**（用户需求 3）。任何一侧修改校验规则，必须同步修改另一侧实现与本文档，并补充篡改攻击测试回归用例，否则视为未完成的变更。

## 1. 契约源文件

| 侧 | 文件 | 职责 |
| --- | --- | --- |
| 后端（权威） | `backend/src/main/java/com/lanlink/shopping/common/ValidationRules.java` | 校验规则唯一权威定义（常量 + 白名单） |
| 前端（镜像） | `frontend/src/utils/validationRules.js` | 同名常量镜像 + 表单形式校验函数 `validateCheckoutForm` |
| 后端消费 | `backend/.../dto/CheckoutDTO.java`（@Size 引用常量）、`service/OrderService.java`（白名单引用常量） | Bean Validation 注解与业务校验均取自契约常量 |
| 前端消费 | `frontend/src/views/Checkout.vue`（提交前 `validateCheckoutForm`） | 表单提交前形式校验 |

## 2. 敏感字段分级

| 级别 | 含义 | 字段 | 后端策略 | 前端策略 |
| --- | --- | --- | --- | --- |
| **L1 服务端权威重算** | 客户端传值一律不可信，后端按商品当前价/规则重算 | 商品价格、订单金额、运费、积分抵扣金额、退款可退余额 | 重算覆盖；客户端传值仅做一致性比对，不一致落 `t_tamper_alert` 告警 | 不传值、不展示为可信来源 |
| **L2 状态机原子流转** | 状态只能由后端条件更新推进，禁止前端指定目标状态 | payStatus、refundStatus、orderStatus、支付状态 | `UPDATE ... WHERE 状态条件` 原子流转，0 行即拒绝 + 告警 | 只发起动作（申请/支付），不传目标状态 |
| **L3 形式校验** | 前后端同规则双重校验 | 收货人、电话、地址、备注、退款原因、支付方式、积分数 | DTO 注解 + 白名单 + 数值边界 | 表单校验同口径 |

## 3. 规则明细（变更须同步三处）

| 规则键 | 值 | 后端 | 前端 | 备注 |
| --- | --- | --- | --- | --- |
| RECEIVER_MAX | 32 | `@Size(max=)` | `RECEIVER_MAX` | 收货人最长字数 |
| PHONE_MAX | 20 | `@Size(max=)` | `PHONE_MAX` | 联系电话最长字数 |
| ADDRESS_MAX | 255 | `@Size(max=)` | `ADDRESS_MAX` | 收货地址最长字数 |
| REMARK_MAX | 255 | `@Size(max=)` | `REMARK_MAX` | 备注最长字数 |
| ALLOWED_PAY_TYPES | `balance / corporate / term` | `OrderService.ALLOWED_PAY_TYPES` | `ALLOWED_PAY_TYPES` | 支付方式白名单，白名单外请求**告警并拒绝** |
| MIN_USE_POINTS | 0 | `usePoints < 0` 拒绝 + 告警 | 输入框 min=0 | 积分使用数非负 |
| IDEMPOTENT_KEY_MAX | 64 | 幂等键长度上限 | 同 | 幂等键防重复提交 |

## 4. 同步维护流程

1. **改规则**：先改 `ValidationRules.java`（权威），再改 `validationRules.js`（镜像），再更新本文档第 3 节表格。
2. **补测试**：在 `backend/src/test/.../TamperAttackSimulationTest.java`（或对应模块测试）补充"新边界值 + 越界值"两类回归用例。
3. **前端回归**：`frontend/src/utils/validators.test.js` / `validationRules` 相关用例同步补齐。
4. **审计**：PR 描述中注明"校验规则变更已同步前端/后端/契约文档"。

## 5. 幂等与并发（对应用户需求 2）

| 机制 | 实现 | 覆盖接口 |
| --- | --- | --- |
| 幂等令牌 | `t_idempotent_token`（`UNIQUE KEY(biz_type, biz_key)`）+ `IdempotentService.reserve/bound/release` | `checkout`（`idempotentKey` 由前端生成 UUID，失败重试复用、成功重置） |
| 状态原子流转 | `OrderMapper.markPaidAtomic`（pay_status 0→1）、`applyRefundAtomic`（refund_status → applied） | 支付、退款申请 |
| 库存原子扣减 | `ProductMapper.deductStockAtomic`（`WHERE stock >= quantity`）、`restoreStockAtomic`（销量 `GREATEST(0,...)`） | 下单扣库存、退款/取消回滚 |
| 账单行锁 | `CreditTermService.repay` 走 `selectForUpdate` | 账期还款 |

> 说明：项目无 Redis 依赖，分布式锁语义由数据库唯一约束令牌表等价实现——多实例并发下同一 `(bizType, bizKey)` 仅有一个事务能插入成功，其余被 `DuplicateKeyException` 拦截。

## 6. 告警与追溯（对应用户需求 4）

- 落库：`t_tamper_alert`（用户、业务类型、字段、客户端值、服务端值、原因、IP、UA、时间）
- 日志：`[tamper-alert]` 结构化 WARN 日志
- 审计：`AuditService` 记录 `TAMPER_ALERT` 动作
- 触发点：非法支付方式、负积分、支付/退款状态机并发拒绝、L1 数值一致性比对失败

## 7. 篡改攻击测试（对应用户需求 5）

模拟第三方工具（Postman/curl）绕过前端直接改参数的场景，见
`backend/src/test/java/com/lanlink/shopping/service/TamperAttackSimulationTest.java`：

| # | 攻击场景 | 期望结果 |
| --- | --- | --- |
| 1 | 篡改 payType 为白名单外值（如 `hack`） | 拒绝 + 篡改告警落库 |
| 2 | 篡改 usePoints 为负数 | 拒绝 + 告警 |
| 3 | 重放同一 idempotentKey 重复下单 | 第二次被幂等拦截"请勿重复提交" |
| 4 | 并发/重放支付（markPaidAtomic 返回 0） | 拒绝 + 告警 |
| 5 | 并发重复退款申请（applyRefundAtomic 返回 0） | 拒绝 + 告警 |
| 6 | 支付方式白名单与前端常量一致性 | 两端白名单集合相等（同步机制守护） |
| 7 | 金额一致性比对（checkNumeric 不一致） | 返回 false + 告警落库 |
