# 营销中台架构设计文档（活动系统 / 促销系统 / 会员系统）

> 版本：1.0　适用仓库：LANLinkshopping
> 定位：面向后续维护与二次开发的技术参考；同时满足「模块化 + 严格隔离 + 事件驱动 + 完整测试」的交付要求。

## 1. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│                        前端（Vue3 + antd）                    │
│  商城(Mall) · 活动中心(/activity) · 会员中心(/membership)      │
└──────────────────────────────┬──────────────────────────────┘
                               │ HTTP /api/**
┌──────────────────────────────▼──────────────────────────────┐
│                     Spring Boot 3（Controller 层）            │
│   /activity/**   /promotion/**   /membership/**   订单 /order │
└──────────────────────────────┬──────────────────────────────┘
┌──────────────────────────────▼──────────────────────────────┐
│                      集成层 integration                       │
│  • PricingFacade  ── 结算价格编排（促销×会员 互斥取优）          │
│  • OrderPaidEvent ── 跨模块事件（Spring ApplicationEvent）      │
│  • Listener  ── MembershipOrderListener / ActivityOrderListener│
└───────┬────────────────┬──────────────────┬──────────────────┘
        │ 独立模块        │ 独立模块          │ 独立模块
┌───────▼───────┐ ┌──────▼───────┐ ┌───────▼───────┐
│ activity      │ │ promotion    │ │ membership    │
│ 活动系统       │ │ 促销系统      │ │ 会员系统       │
│ t_activity    │ │ t_promotion  │ │ t_member_level│
│ t_activity_   │ │              │ │ t_member_card │
│  participant  │ │              │ │ t_member_     │
│               │ │              │ │  point_log    │
└───────────────┘ └──────────────┘ └───────────────┘
```

### 1.1 模块化与隔离原则
- 三个营销模块位于独立包 `com.lanlink.shopping.module.{activity|promotion|membership}`，**每个模块拥有独立的 entity/mapper/service/controller，互不 import 对方的业务类**。
- 模块间不直接调用，只通过**集成层**通信：`PricingFacade`（同步方法调用）与 `OrderPaidEvent`（异步事件监听）。
- 集成层是唯一感知多个营销模块的组件；订单系统只依赖 `PricingFacade` 与事件发布，不触碰任何营销模块内部实现。
- 营销侧监听器使用 `REQUIRES_NEW` 独立事务 + 异常捕获：营销处理失败不回滚订单支付（核心交易隔离）。

## 2. 数据模型

| 表 | 归属 | 关键字段 | 说明 |
| --- | --- | --- | --- |
| t_activity | 活动 | activity_id, title, type(register/purchase), status | 活动定义；status 0未开始/1进行中/2已结束 |
| t_activity_participant | 活动 | activity_id, user_id, bonus_points | **UNIQUE(activity_id,user_id)** 保证同一活动不可重复参与（防冲突） |
| t_promotion | 促销 | promo_id, type(full_reduce/discount), threshold, benefit_amount, discount_rate, scope(all/ind), ind_id | 满减/折扣规则；scope 支持全场或行业限定 |
| t_member_level | 会员 | level_id, level_name, min_growth, discount_rate | 等级体系（种子：普通/白银/黄金/钻石） |
| t_member_card | 会员 | user_id(**UNIQUE**), level_id, growth, points | 每用户一张会员卡 |
| t_member_point_log | 会员 | user_id, change_type, change_val, ref_order_no | 积分流水（可审计） |

## 3. 事件处理机制（跨模块通信协议）

```
OrderService.pay()
   └─ publishEvent(OrderPaidEvent{userId, orderNo, amount})
        ├─► MembershipOrderListener  → earnGrowth() 累计成长值/积分 + 等级自动升级
        └─► ActivityOrderListener    → autoJoinPurchase() 自动参与「消费有礼」活动（幂等）
```
- 事件定义：`integration.event.OrderPaidEvent`（继承 `ApplicationEvent`）。
- 隔离保证：发布方（订单）不感知任何营销模块；监听器注册在集成层，异常被吞并记日志，不影响支付主流程。
- 幂等：活动参与受唯一约束保护；积分流水按订单维度由调用方保证单次支付仅触发一次。

## 4. 价格编排（冲突防止核心）

`PricingFacade.quote(userId, orderAmount, orderIndId, memberEligible)`：

```
促销优惠 = PromotionService.calculateDiscount(amount, indId)   // 满减/折扣，多规则取最大
会员优惠 = memberEligible ? amount × (1 - 等级折扣率) : 0        // 仅采购方身份
最终价   = max(amount - 促销优惠 - 会员优惠, 0)                 // 互斥：两者不叠加，取优惠更大者
```

**冲突防止规则**（明确定义，杜绝叠加套利）：
1. 促销优惠 与 会员折扣 **互斥**，取对用户更优惠者，另一来源归零；
2. 同一类型多促销规则时取最大优惠（PromotionService 内部）；非启用/非时间窗内促销一律跳过（含防御性校验）；
3. 商户/管理员身份不享有会员折扣（仅采购方 role_id=1）。

## 7. 部署与扩展指引

- 表结构由 `schema.sql` 幂等创建 + 种子（会员等级）；演示活动/促销由 `DataInitializer.seedMarketingDemo()` 按标题幂等写入。
- **新增营销模块**：在 `module` 包下建立独立子包（entity/mapper/service/controller），需要跨模块能力时在 `integration` 层定义新事件或扩展 Facade。
- **新增促销类型**：`PromotionService.calculateDiscount` 中按 type 扩展分支即可，无需改动其他模块。
- **会员等级调整**：直接改 `t_member_level` 种子/数据，等级折扣自动生效于结算。

## 8. 验证记录（端到端）

1. `GET /activity/list` 返回 2 条进行中活动（注册有礼 + 消费有礼）；
2. `POST /activity/{id}/join` 成功且重复参与被拒；
3. `GET /membership/my` 返回会员卡/等级体系/积分流水/积分规则；
4. 下单结算：促销满减与会员折扣按互斥规则取优计入订单总额；
5. 订单支付触发事件：会员成长值/积分累计（VIP 双倍）、消费活动自动参与，均落库成功；
6. **积分抵现闭环**（2026-10-04 实测，14 项断言全部通过）：
   - 无积分下单 1950 元 → 支付后按 1 元 = 1 积分获得 1950 积分（earn_consume 流水落库）；
   - `redeem-quote` 试算 1950 积分：单笔 10% 上限 = 195 元，实际按 1000 积分 = 1 元、整元抵扣（1950 分归整为 1000 分）抵 1 元（双重约束取更严者）；
   - 携带 `usePoints=1950` 下单：应付 1950 − 19.50 = 1930.50 元，积分余额 1950 → 0（redeem_order 流水 −1950）；
   - 取消订单：积分全额返还 0 → 1950（refund_order 流水），重复取消幂等不重复返还；
   - 前端 Checkout 页积分区块（余额/试算/合计联动）与会员中心积分规则卡片构建通过。
